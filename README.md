# Дополнительные тесты

Помимо обязательного списка (регистрация → редирект → логин, sad path создания новости, детальная страница новости, пагинация, обновление профиля), в набор добавлены следующие тесты.

## Безопасность

`test_pii_article_id_returns`, `test_no_pii_leak_api_article`

UI нигде не показывает email и телефон автора — но их видно только глазами через интерфейс. Любой, кто откроет DevTools или дёрнет API напрямую, получит эти данные из ответа `/api/news` и `/api/news/{id}/comments`. Ручное тестирование через UI такую утечку не обнаружит в принципе, потому что она не на экране — нужна отдельная проверка сырого ответа API.

## Известные баги продукта

`test_invalid_fields_register`, `test_create_article_with_image`, `test_update_profile_with_set_photo`

Баги уже найдены и подтверждены вручную. Тесты закреплены в наборе не для того, чтобы проходить, а чтобы регрессия была видна: если баг случайно починят на бэкенде без нашего ведома, тест позеленеет и это будет сигналом; если кто-то сломает что-то рядом — тест не потеряется среди прочих проверок.

Битые ссылки на изображения — не только в карточке своей новости и на странице профиля: `test_update_profile_with_set_photo` дополнительно проверяет, что после загрузки фото аватар в шапке сайта (виден на любой странице, не только в профиле) тоже не загружается — баг задевает компонент, переиспользуемый по всему сайту, а не только место непосредственной загрузки.

## Контракт API в обход UI

`test_valid_article_id_returns`, `test_correct_answer_api_article`, `test_valid_answer_me_api`, `test_valid_answer_login_api`, `test_invalid_article_id_returns_404`, `test_incorrect_page_api_article`, `test_incorrect_page_api_article_empty`, `test_incorrect_per_page_api_article`

UI-тест на happy path проверяет только то, что видно на экране — если бэкенд начнёт отдавать лишнее поле, неправильный тип или неверный статус на невалидный запрос, страница может отрисоваться нормально, а баг всплывёт только у стороннего клиента API. Эти тесты бьют по API напрямую, минуя рендеринг, поэтому ловят рассинхрон бэкенда со схемой и некорректную обработку граничных параметров (`page`, `per_page`, несуществующий `id`) быстрее и точнее, чем сквозной UI-тест.

## Состояния, недостижимые на живом сайте (мок API)

`test_empty_news_feed`, `test_news_feed_server_error`

Сайт общий и постоянно наполнен данными от других студентов — гарантированно получить пустую ленту или ответ 500 от реального бэкенда нельзя, а UI обязан не ломаться в обоих случаях. `page.route()` подменяет ответ `/api/news` напрямую в браузере, не трогая реальный сервер, и позволяет детерминированно воспроизвести оба состояния. Заодно вскрылось: фронт не различает "данных нет" и "сервер упал" — оба случая молча показывают одно и то же сообщение "Ничего не найдено", без индикации реальной ошибки.

## Дополнительное покрытие UI

`test_correct_sorted_news`, `test_correct_search_article`, `test_incorrect_search_article`, `test_correct_clear_search_article`, `test_logout`, `test_exists_email_register`, `test_invalid_password_register`

Каждый из этих сценариев — реальное действие, доступное пользователю в интерфейсе (сортировка ленты, поиск и его сброс, выход из аккаунта, повторная регистрация на занятый email, короткий пароль), но не входящее в обязательный список. Оставлять их непокрытыми означало бы полагаться на то, что баг в этих местах просто никогда не появится.
